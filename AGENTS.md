# AGENTS.md

This file documents the globally installed Go-specific subagents available in this environment and when to reach for each one on this project. It's self-contained — read `CLAUDE.md` first for project context, then use this as a reference for delegating work.

**Important caveat:** this guidance is written from each agent's name and inferred purpose, not from reading their actual agent-definition files (they're installed globally, e.g. under a `~/.claude/agents/` style directory, and aren't part of this repo). If an agent's actual behavior, tools, or scope diverges from what's described here, trust the agent's own definition over this file, and update this file to match once you notice the mismatch.

The project follows DDD + hexagonal architecture (see `CLAUDE.md`'s Architecture section): `internal/domain` (pure, no I/O), `internal/application` (use cases + ports), `internal/adapters/*` (implementations of ports, both driven/secondary and driving/primary). Agent selection below is organized around that split.

## Available agents

- **`go-scaffold`** — initial project/module setup: `go.mod`, the `domain`/`application`/`adapters` directory layout, base tooling config. Use once, near the start, to lay down the structure proposed in `CLAUDE.md`'s "Proposed project layout".
- **`go-feature`** — implementing a discrete piece of functionality end-to-end, spanning `domain`/`application` as needed. This is the main workhorse for turning one piece of the reverse-engineered protocol into working Go — e.g. "implement `Frame` encode/decode in `internal/domain` per findings-doc section 12.2a/12.3a", "implement `APSession`'s handshake in `internal/application` per section 12.3, against the `Transport` port", "implement the relay-mode registration + NAT-traversal handshake per section 12.2", "implement the SD-card file-listing/download use cases per section 12.6". Also the right choice for adapters that are protocol-specific rather than generic-pattern (i.e. `adapters/transport/aptcp` and `adapters/transport/relay/*` — these implement the `Transport` port against Naxclow's actual wire protocol, which isn't a generic "build an API client" task).
- **`go-api-builder`** — HTTP API client work. Use specifically for `internal/adapters/naxclowapi` (the naxclow cloud REST client implementing the `CloudAPI` port: `login`/`register`, `getDevicesListByType`, `watching`, `getA9VideoConf` — see findings doc sections 4 and 8/Mode A) — only relevant if/when cloud-relay mode gets built. Don't use this for the `Transport` adapters above — those are custom binary protocol work, not a REST API client.
- **`go-db-builder`** — persistence/storage layer. Likely **not needed** for the core protocol client. Only reach for this if the project grows a need to cache device configs, credentials, or session state locally — don't scaffold a DB layer preemptively, and don't let it leak into the domain layer if it does get added (a cache is a driven adapter behind its own port, same as everything else).
- **`go-cli-builder`** — `internal/adapters/cli` and `cmd/v720ctl`, the primary/driving adapter — e.g. discover/connect/live-view/record/list-files subcommands, calling into `application.Session`/`application.SessionManager`. Should contain no protocol logic itself — if you find wire-format or handshake logic creeping into the CLI adapter, that's a layering violation, move it to `application`.
- **`go-refactor`** — cleanup and renaming passes. Particularly relevant here: early implementation will lean on the naming map in `CLAUDE.md`, which will get refined as protocol understanding deepens (especially once the still-obscured command codes and field names get resolved). Also the right tool for enforcing/restoring the domain→application→adapters dependency direction if it drifts. Use this agent to propagate renames consistently across the codebase rather than doing it by hand, and update `CLAUDE.md`'s naming table in the same pass.
- **`go-reviewer`** — code review before merging. **Use this on every piece of wire-protocol code** — `Frame` parsing, handshake state machines, command-code tables, frame reassembly logic (all `domain`/`application` layer). Also use it to catch architecture-boundary violations (domain importing an adapter, application importing a concrete adapter type instead of depending on its own port). This is the area most likely to have a subtle byte-order, field-offset, or off-by-one bug that only shows up against a real device, and the cost of catching it in review is much lower than the cost of catching it while staring at a non-working camera stream.
- **`go-test-generator`** — test generation. Prioritize for: `Frame` encode/decode round-trip tests (byte-exact, ideally with fixed test vectors derived directly from the findings doc's tables — pure `domain` tests, no mocks needed), `application`-layer handshake state-machine tests (against a fake/mock `Transport` port — this is exactly what hexagonal architecture makes easy: no real socket needed to test `APSession`'s handshake logic), and command-code coverage (one test per documented code, asserting the exact JSON shape produced).
- **`go-docs-generator`** — package/API documentation generation. Use once an API surface (e.g. the `Session`/`Transport`/`CloudAPI` port interfaces, or the `cmd/v720ctl` CLI) has actually stabilized — not while it's still actively changing, since generated docs will just need regenerating.

## Suggested workflow per unit of work

Per `CLAUDE.md`'s "Workflow: small steps, one branch per step, test-first" — every step below happens on its own branch, scoped to one small piece of work, merged before the next one starts.

1. **Branch.** Create a new branch scoped to exactly one step (one type, one port, one adapter, one use case, one handshake step) — nothing else rides along.
2. Check the findings doc (`CLAUDE.md` → doc reference) for what's being implemented. Note whether the relevant detail is confirmed or flagged unconfirmed/inferred (doc sections 7 and 12.8).
3. If unconfirmed, or the doc simply doesn't cover it, cross-check the jadx-decompiled source (path in `CLAUDE.md`) before writing code — don't guess at wire-format details. Update the doc with whatever you find, so the next session benefits.
4. **Test-first wherever the doc already specifies the exact expected behavior** (true for most `domain`-layer work — byte tables, JSON command shapes, handshake sequences are all fully documented): write the test via `go-test-generator` (or by hand) asserting the documented behavior, confirm it fails, then implement via `go-feature` (or `go-api-builder`/`go-cli-builder` for those specific adapters) until it passes. For behavior that isn't pinned down yet, a short spike is fine, but land a regression test in the same branch before moving on.
5. Run `go-reviewer` before merging — not optional for protocol-critical work, and also the point to catch architecture-boundary violations (see `CLAUDE.md`'s dependency-direction rule).
6. Merge, then start the next step on a fresh branch.
7. Periodically run `go-refactor` to keep naming consistent with `CLAUDE.md`'s naming map as it evolves, and `go-docs-generator` once an area has stabilized.

## Known open items — verify, don't guess

The findings doc's section 12.8 ("Remaining gaps") lists specific unresolved details as of when it was written: a handful of obscured command codes (`instLed`, `motorState`, `setRf433Dev`, `sfq`, two SD-card delete-picture codes, and one JSON field name in the relay-mode register message), a few unconfirmed byte-offsets in the `Frame` header, the exact relationship between the relay-mode TCP-phase and UDP-phase NAT candidates, and `connectDirect` (local-LAN discovery for STA-mode devices, i.e. camera already on the home WiFi rather than in its own AP hotspot) — not yet traced at all. Any of these should be resolved by checking the jadx source directly (and updating the doc) before being treated as settled — not guessed at or silently assumed correct.
